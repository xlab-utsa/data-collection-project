data-collect-system

Edge devices (NVIDIA Jetson boards with cameras) capture high-quality video, compress it, packetize it and stream it to a central storage server, which reassembles, decodes and records it.

Overview

The project has a working starting point and a clear destination. This page explains the code as it is today, describes what the finished system should do, and lists the steps in between.

A working single-device baseline

One sender captures from a camera, encodes with VP9 on the CPU (libvpx), and streams over UDP with ACKs and retransmission. One receiver reassembles, decodes and records the stream to disk.

A fleet of edge cameras feeding one server

Many Jetson devices capture continuously, encode on the GPU, transmit on separate CPU cores with the stages overlapping, share the server's bandwidth fairly, and adapt to congestion. See Goal.

How the current code works

A sender on the edge device and a receiver on the storage server, talking over UDP. The diagram follows the README.

  1. Handshake. The receiver sends a ConfigMsg that carries only the target bitrate, and re-sends it every 500 ms until the sender answers. The sender replies with width, height, fps and bitrate.
  2. Capture (capture.cc). The camera delivers packed YUYV. Each frame is converted to planar I420 (with libswscale) directly into a free slot of the FrameRing. If the encoder falls behind and the ring is full, the new frame is dropped and counted.
  3. Encode and send (video_sender.cc, encoder.cc). A timer fires once per frame interval. Each tick takes the oldest frame from the ring and encodes it on the main thread: libvpx VP9, real-time single-pass CBR with key frames only on demand. The encoded frame is split into datagrams of at most MTU − 28 − 17 bytes.
  4. Reliability. The receiver ACKs every datagram. When an ACK arrives, unacked datagrams sent before it are queued for retransmission, up to 3 times and at most once per RTT. If the oldest unacked datagram is more than 1 s old, the sender gives up, clears its queues and forces a key frame.
  5. Feedback. About once a second the receiver piggy-backs its measured goodput (kbps × 100) on an ACK. The sender only logs it: no adaptation exists yet.
  6. Decode and record (decoder.cc). Complete frames go in order to a worker thread, which decodes them, appends them to data/output_YYYYmmdd_HHMMSS.y4m and, with --lazy 0, also displays them. On Ctrl+C it finishes the queued frames and closes the file.

Threads today

Sender

  • capture thread: camera → I420 → FrameRing
  • preview thread: the preview window
  • main thread: encodes and does all network I/O

Receiver

  • main (network) thread: receive, ACK, reassemble
  • decode/record worker: decode, write .y4m, display

Goal

What the finished system should do. This describes the target behaviour, not how to build it; working that out is the job of the roadmap.

GOAL 1

Capture continuously

Some CPU cores pick frames up from the camera into a ring buffer, which is written, read and freed continuously.

GOAL 2

Encode on the GPU

The Jetson boards this targets have no hardware video encoder (NVENC), so compression work has to run on the GPU (CUDA) rather than on dedicated encoder hardware.

GOAL 3

Package and transmit

Encoded frames are packaged and transmitted on other CPU cores.

GOAL 4

Stagger the stages

The stages overlap: while the GPU encodes frame N, the capture cores already grab frame N+1 and the transmit cores send frame N−1.

GOAL 5

Share the server fairly

Many devices stream to one storage server and compete for its bandwidth. Congestion has to be measured and reported between server and devices.

GOAL 6

Adapt

Each device adjusts everything that can be adjusted to fit what the network and server can take, while losing as little useful data as possible.

Overlapping stages on one device

Many devices, one server

What a device can adjust

bitrate frame rate resolution dropping frames

Each device should back off under congestion and recover afterwards, while losing as little useful data as possible. When and how to use each knob is part of roadmap item 5.

Known limitations

These are the starting points for the roadmap.

  • One thread for encoding and sending. The sender encodes and does all network I/O on the same thread, so a slow encode delays ACK processing and sending, and nothing overlaps.
  • CPU-only encoding. Encoding runs on the CPU through libvpx.
  • The ring uses a mutex and is FIFO. If the encoder is slower than the camera, frames queue up and age, so latency grows until the ring fills.
  • Bitrate, fps and resolution are fixed. The goodput feedback is only logged.
  • One device per receiver process.
  • No per-stage latency measurement. There are only coarse per-frame logs (-o).
  • No reorder tolerance. Any datagram older than one that was acked is treated as lost.
  • The receiver display uses vsync. With --lazy 0 at fps above the monitor's refresh rate, use --lazy 1 for recording.
  • Not yet validated on Jetson hardware.

Roadmap

Each item says what to build, why, how we know it is done, and what to read up on. Items roughly build on each other, but several can proceed in parallel. Measure before and after every change; item 1 gives you the tools for that.

  1. 1Per-stage latency benchmarking

    Goal
    Know where the time goes. Timestamp every frame at each stage on both machines: capture, ring wait, conversion, encode, send queue, transmit, network, reassembly, decode and write. Report per-stage and end-to-end latency distributions.
    Done when
    One command turns a sender log and a server log into a per-stage table of p50, p95 and p99, and end-to-end latency is reported correctly when the two machines' clocks are synchronized.
    Pointers
    clock_gettime (CLOCK_MONOTONIC vs CLOCK_REALTIME)chrony and PTP clock synchronizationpercentiles vs averagestail latency

  2. 2Staged pipeline and latency hiding

    Goal
    Split the sender into separate capture, encode and packetize/transmit stages on separate threads and cores, so the stages overlap. Then use the measurements from item 1 to find the slowest stage and break it up further, so more of the work hides behind other work.
    Done when
    Sustained throughput is limited by the slowest stage rather than the sum of all stages, the event loop never blocks on encoding, and the per-stage numbers show the overlap. The before/after comparison is documented.
    Pointers
    pipeline parallelismAmdahl's lawpthread_setaffinity_np and isolcpuseventfdVP9 tiles and row multi-threadingdouble-bufferingpacket pacing

  3. 3A better ring buffer

    Goal
    A ring between capture and encode that never blocks either side, keeps latency bounded when the consumer falls behind, and avoids extra copies of frame data.
    Done when
    A stress test with two threads passes, latency stays bounded when the encoder is artificially slowed, and the ring's overhead is measured.
    Pointers
    single-producer/single-consumer queuesstd::atomic memory ordering (acquire/release)false sharing and cache-line alignmentdrop policies (drop newest vs drop oldest)

  4. 4GPU offload on Jetson (no NVENC)

    Goal
    Move per-frame pixel work (colour conversion, scaling) onto the GPU first, then the compression work itself, so the CPU cores are free for capture and networking.
    Done when
    GPU output matches a CPU reference (bit-exact for conversion), the encode stage keeps up at the target modes on a Jetson, and CPU load drops measurably.
    Pointers
    CUDA streams and asynchronous copiespinned and unified memory on JetsonNVIDIA NPP and VPInvJPEGwhich Jetson modules lack NVENCmotion estimation on GPUs

  5. 5Congestion feedback and adaptation

    Goal
    The server measures what it receives (goodput, frame loss, queuing delay) and reports it to the device. The device reports its own state to the server. The device then adapts bitrate, frame rate and resolution, and drops frames when needed, so it backs off under congestion and recovers afterwards.
    Done when
    Under emulated congestion (tc netem, bandwidth limits) the stream adapts within a bounded time without oscillating, and recordings stay decodable. The receiver starts a new recording file when the resolution changes.
    Pointers
    AIMDGoogle Congestion Control (GCC)RFC 8698 (NADA)RFC 8888 (RTP congestion-control feedback)libvpx vpx_codec_enc_config_setspatial and temporal scalability (SVC)

  6. 6Multi-device storage server

    Goal
    One server process that receives from many devices at once and shares its bandwidth fairly among them, telling each device its budget.
    Done when
    Several senders stream to one server at the same time, each is recorded separately, and the bandwidth split follows the chosen fairness policy as devices join and leave.
    Pointers
    max-min fairnessepollper-connection session statedevice identity and registration

  7. 7Storage without decoding

    Goal
    Let the server store the compressed stream directly, with decoding optional, so it can serve many devices cheaply.
    Done when
    Recordings play back in standard players and contain timestamps.
    Pointers
    the IVF containerWebM/Matroska (libwebm)

  8. 8Building parts in Rust

    Goal
    Move the components that benefit most from memory safety and safe concurrency to Rust, while keeping V4L2, CUDA and libvpx code in C/C++. Candidates: parsing of untrusted network input (the wire protocol), the storage server, the congestion and fairness logic, and queues shared between threads.

Building parts in Rust

Roadmap item 8. The goal is not a rewrite: move the parts that gain the most from Rust's guarantees, and leave the hardware-facing code where it is. How to split the work and design the interfaces is up to you.

Candidates for Rust, and why

  • Parsing of untrusted network input (the wire protocol). Anything on the network can send a malformed packet; memory safety means such input cannot corrupt memory.
  • The storage server. It handles many connections at once, where safe concurrency helps.
  • The congestion and fairness logic. Self-contained decision logic that is easy to test in isolation.
  • Queues shared between threads. Concurrency bugs here are hard to find; the compiler checks how data is shared.

Stays in C/C++

  • V4L2 camera code
  • CUDA code
  • libvpx code

Done when

A Rust crate builds with cargo, links into the existing binaries through a C ABI (or the server is a Rust binary speaking the same wire format), and has parity tests that check it against the C++ implementation.

What to read up on

extern "C" and #[no_mangle] cbindgen the cxx crate bindgen and the cc crate in build.rs the staticlib crate type fuzzing with cargo fuzz tokio for the server

Setup & testing

Ubuntu 22.04 or later, or JetPack on a Jetson.

Dependencies

shell
sudo apt install build-essential autoconf automake pkg-config \
     libvpx-dev libsdl2-dev libavutil-dev libswscale-dev
  • No camera? Use a virtual V4L2 camera (v4l2loopback) fed by FFmpeg; see below.
  • For roadmap work: the CUDA toolkit (part of JetPack on Jetson; on a PC from NVIDIA's site), and Rust via rustup for the Rust items.
  • For viewing recordings: sudo apt install ffmpeg.

Build

shell
./autogen.sh
./configure
make -j

This produces src/app/video_sender, src/app/video_receiver and src/video/webcam. The standalone recorder is built separately; see the comment at the top of tools/capture_to_disk.c. The code is compiled with -Wall -Wextra -Werror -Weffc++, so warnings fail the build.

Unit tests

These need no camera and no media libraries.

shell
make -C tests run

They cover the wire protocol (round trips, truncated and random input), the frame ring (ordering under two threads, drop-when-full) and the handshake over loopback (including a receiver that starts before the sender). Add a test for every module you change.

End to end on one machine with a virtual camera

install the virtual camera module
sudo apt install v4l2loopback-dkms
create the virtual camera
sudo modprobe v4l2loopback devices=1 video_nr=10 exclusive_caps=1
feed it a test pattern
ffmpeg -re -f lavfi -i testsrc2=size=1280x720:rate=60 -pix_fmt yuyv422 -f v4l2 /dev/video10

Then, in two other terminals:

sender
./src/app/video_sender 9000 -w 1280 -h 720 -r 60 -d /dev/video10 --no-preview
receiver
./src/app/video_receiver 127.0.0.1 9000 --cbr 6000 --lazy 1

Stop both with Ctrl+C. Check that a .y4m file appeared in data/ and that it plays (see Viewing a recording).

Network conditions

To see loss recovery, add loss or delay on the loopback interface with tc netem, and remove it when done:

add loss and delay
sudo tc qdisc add dev lo root netem loss 2% delay 20ms
remove it
sudo tc qdisc del dev lo root

On a Jetson, use the real camera (/dev/video0) and run the receiver on another machine on the same network.

History

This project started as a copy of YuxinLiu2023/video_capture-stream_v2, which builds on Microsoft's Ringmaster (VP9 over UDP with per-datagram ACKs). The original commit history is kept in the repository. On top of it, the code was refactored, commented and fixed:

  • Builds again. Upstream encoder.cc referenced an undeclared member, so it did not compile.
  • Camera buffers. V4L2 used to keep only the last buffer mapping and read frames outside it. Every buffer is now mapped and looked up by index.
  • Large frames. The fragment count was wrong for frames larger than about 2 MB, so the last datagram exceeded the MTU. Large key frames at 4K/8K are affected.
  • Shutdown. Ctrl+C used to crash the sender. On the receiver it lost the buffered recording and never joined the decoder thread. Both programs now shut down cleanly.
  • Display while recording. With --lazy 0 the window used to stay empty: each decoded frame was used for the file and was then gone.
  • Decode buffer. The fixed 1 MB buffer overflowed on large key frames.
  • Handshake. It now retries, and malformed or stray packets no longer crash either side.
  • Y4M output. Recordings now have square-pixel aspect, and the standalone recorder writes valid 4:2:2 Y4M.
  • Repository. Generated build files were removed from git, a .gitignore was added, and unit tests were added.
